## Voice milestone completion — custom wake word, device config, self-hearing mitigation, error handling

**Status: IMPLEMENTED / CODE INSPECTED — PI VERIFICATION REQUIRED.** Builds directly on the checkpoint above (still commit-checkpoint state, not yet run on the Pi). This round closes the remaining gaps the checkpoint explicitly flagged as outstanding — generic wake word, no device config, no self-hearing mitigation, thin error handling — using the same real-implementation-first discipline (every API claim below was verified against actual package docs/source, not assumed).

- **Custom "Hey Ciphlet" wake word — provisioned, not fabricated.** Verified openWakeWord's actual custom-training pipeline (`dscripka/openWakeWord`'s own `notebooks/automatic_model_training.ipynb`, fetched and inspected directly) rather than assuming a lightweight path existed. It's a genuine GPU-class training job: ~15 extra ML packages (`torch`, `torch-audiomentations`, `speechbrain`, `tensorflow-cpu==2.8.1`, etc.) and tens of GB of precomputed negative-audio features (~2,000 hrs ACAV100M + AudioSet/FMA/room-impulse-response data), targeting ~10 min on a free Colab T4 GPU per the upstream project's own documentation. Running this on the Pi (ARM, no GPU) or the Mac (project rule: no Ciphlet runtime/training workloads there) would be wrong, not just slow. `deploy/wake_word/TRAINING.md` documents the real, verified procedure (exact Colab notebook URL, the real `config["target_phrase"] = [...]` / `config["model_name"] = ...` edit pattern the upstream notebook itself uses, and an honest note that "Ciphlet"/"Hey Ciphlet" is a novel word whose synthetic-TTS pronunciation should be checked and the phrase spelling adjusted if needed — same technique openWakeWord's own community already uses for uncommon names). `deploy/install_voice.sh` now checks for a trained `models/wake/hey_ciphlet.onnx` and wires it into the printed `CIPHLET_WAKE_MODEL` line automatically if present; falls back to the generic pretrained models (documented in the checkpoint above) otherwise. No `ciphlet/voice/providers.py`/`pipeline.py` code changes were needed to *consume* a trained model — `OpenWakeWordProvider(model_path=...)` already supported this.
- **Microphone/speaker device configuration** — new `CIPHLET_AUDIO_INPUT_DEVICE` (PortAudio, via `sounddevice`) and `CIPHLET_AUDIO_OUTPUT_DEVICE` (ALSA, via `aplay -D`) config fields (`ciphlet/config.py`), since the Pi's default audio device is not guaranteed to be the intended mic/speaker (e.g. a USB mic or HAT). Wired into `PTTVoiceSession`/`HandsFreeVoiceSession` (input) and `PiperTTS` (output). Documented device-listing commands (`python3 -m sounddevice`, `aplay -L`) rather than reimplementing device enumeration — both already do this natively.
- **Self-hearing / false-reactivation mitigation** — `HandsFreeVoiceSession` previously treated a single VAD-positive frame during TTS playback as a real interruption, which would misfire on Ciphlet's own voice bleeding back into the mic (no hardware AEC exists — `AudioProcessor.condition()` is still a documented pass-through placeholder). Added `BARGE_IN_DEBOUNCE_FRAMES` (`ciphlet/voice/pipeline.py`): requires ~90ms of *sustained* speech before treating it as a genuine barge-in. Documented explicitly as a heuristic, not true acoustic-echo cancellation — real AEC remains future work, unchanged from the prior round's scope note.
- **Barge-in / TTS interruption correctness fix** — `PiperTTS.stop()` previously only killed the `aplay` playback subprocess, leaving the `piper` synthesis subprocess itself unterminated (a real latent bug: with the parent never closing its copy of `piper.stdout`, a killed player could leave `piper` blocked writing to a pipe with no reader, i.e. an orphaned process on repeated barge-ins). Fixed by tracking and terminating both subprocesses in `stop()`, and adopting Python's own documented two-process-pipe idiom (`piper.stdout.close()` in the parent right after wiring up the player) so `piper` gets a normal SIGPIPE instead of hanging.
- **Voice error handling** — `PiperTTS.speak()` now captures both subprocesses' stderr and raises `VoiceUnavailableError` with the actual failure output on a non-zero exit (previously silent — a failed synthesis or playback looked identical to success). `VoskSTT`, `OpenWakeWordProvider`, and `WebRTCVadAudioProcessor` now wrap model/VAD construction and convert a bad model path or invalid config into a clear `VoiceUnavailableError` instead of a raw low-level exception. `PTTVoiceSession`/`HandsFreeVoiceSession` now open the input stream through a shared `_open_input_stream()` helper that converts `sounddevice.PortAudioError` (no mic, wrong device, device busy) into the same clear, actionable error type, and both properly `stream.stop()`/`stream.close()` on exit instead of relying on a bare context manager.
- **Shared voice/text parity** — `HandsFreeVoiceSession` gained an optional `on_reply` hook (pipeline.py stays decoupled from `Orchestrator`, same as before — it's still just a `Callable`), wired in `main.py` to print the same `[brain] <identity> — N message(s) in context — <timing>` line that text mode and push-to-talk already print. Previously hands-free voice had no observability into which brain served a reply; this was an explicitly tracked, now-closed gap from the prior round (see "Known incomplete" above).
- **VAD, VOSK STT, Piper TTS, push-to-talk, and the shared `Orchestrator.handle_text` conversation/memory path were already implemented and unchanged in substance** — this round only added the device/error-handling/debounce layer around them, not a redesign.
- **Mac-side verification performed** (proportional — no mic/speaker/Ollama/VOSK hardware, and per project rule, no voice runtime dependencies installed on the Mac): `python3 -m py_compile` on every touched `.py` file, `bash -n` on both installer scripts, and a grep-based check that every constructor call site for the changed classes (`PiperTTS`, `VoskSTT`, `OpenWakeWordProvider`, `WebRTCVadAudioProcessor`, `PTTVoiceSession`, `HandsFreeVoiceSession`) matches the new signatures. None of this is a substitute for real Pi audio hardware behavior.

## Pi hardware finding — USB mic rejects 16 kHz (`paInvalidSampleRate`)

**Status: IMPLEMENTED / VERIFIED OFF-PI WITH A FAKE AUDIO DEVICE — PI RE-TEST REQUIRED.** Real Pi finding: the USB mic (ALSA `hw:2,0`) is detected, but `ciphlet voice --ptt` failed with `paInvalidSampleRate` (`PaErrorCode -9997`). `arecord --dump-hw-params -D hw:2,0 /dev/null` reports `FORMAT: S16_LE`, `CHANNELS: 1`, `RATE: [44100 48000]` — the hardware does not support 16 kHz.

- **Where the rate was fixed:** `ciphlet/voice/pipeline.py::_open_input_stream` opened `sd.InputStream(samplerate=SAMPLE_RATE=16000, ...)` for both `PTTVoiceSession` and `HandsFreeVoiceSession`; every reader then did `stream.read(FRAME_SAMPLES=480)`. Nothing else in the codebase touches capture.
- **Downstream requirements (from source):** webrtcvad `is_speech(frame, 16000)` on 480-sample/30 ms frames; openWakeWord 16 kHz int16 in 1280-sample windows; VOSK `KaldiRecognizer(model, 16000)` (16 kHz small model). All three are unchanged and still receive exactly 16 kHz mono int16.
- **Fix (capture boundary only):** `_open_input_stream` now probes rates in order 16000 → 48000 → 44100 → the device's own default, falling through only on `paInvalidSampleRate` (`PortAudioError.args[1] == -9997`); any other PortAudio error (no mic, busy, wrong device) still raises the original actionable `VoiceUnavailableError` immediately. If 16 kHz opens, the raw stream is returned exactly as before (no behavior change for devices that already worked). Otherwise it returns `_ResamplingInputStream`, which exposes the same `read/stop/close` surface and delivers 16 kHz frames, so no call site changed. 48 kHz is preferred over 44.1 kHz (clean 3:1). The working rate is cached per device (PTT reopens the stream every turn) and the resampling is announced once. `CIPHLET_AUDIO_INPUT_DEVICE` is forwarded to every open attempt unchanged.
- **Resampler (`_StreamResampler`, numpy only, no new dependency):** stateful Kaiser-windowed-sinc interpolation with the cutoff just under the 8 kHz output Nyquist, so out-of-band content is filtered rather than aliased into the speech band, and filter state carries across blocks so there are no per-30 ms edge glitches. Measured off-Pi: tones up to 3.4 kHz match an ideal 16 kHz sine to within 1 LSB; 6 kHz −0.4 dB; 9 kHz −40 dB; 10 kHz −80 dB (naive decimation would alias 10 kHz to a full-strength 6 kHz tone); output identical for any input block size; ~0.05 ms CPU per 30 ms frame on the Mac. Adds ≈ one 30 ms frame of queue latency at startup.
- **Tests:** `tests/test_audio_input.py` (19 tests, fake `sounddevice`, no hardware): 48k-only and 44.1k-only mic, native-16k passthrough, device-default last resort, device setting forwarded, rate cache, non-rate errors not retried, exhaustive-failure message, and the resampler numerics above plus an end-to-end check that `HandsFreeVoiceSession._check_wake` receives 1280-sample 16 kHz windows from a 48 kHz mic. Numeric tests need numpy and skip without it; they were run in a throwaway numpy-only venv outside the repo (the Mac has no voice deps installed, per project rule).
- **Not verified (needs the Pi):** real PortAudio behavior on `hw:2,0` at 48 kHz, actual VAD/wake/VOSK accuracy on the resampled mic audio, and whether the mic's input level needs adjusting (`alsamixer`). The output side (Piper → `aplay`) was not part of this finding and is untouched.

### Local Qwen, round 2 — root cause and fix for the 180s timeout/hang

**Diagnosis (two independent, complementary causes identified from the reported evidence, not guessed):**

1. **Unbounded prompt vs. a small context window.** The reported subprocess included the full system prompt (identity + memory-continuity instructions) plus all 12 resumed messages, bounded only by `-c 2048` with no input-side sizing. Reconstructing that exact shape on Mac (12 realistic prior messages + system prompt) estimates ~2225 tokens — already over the 2048-token window before the 256-token output reserve. Once a prompt reaches/exceeds `-c`, llama.cpp must context-shift/reprocess, which is dramatically slower than normal prompt processing and can plausibly exceed 180s. The previous implementation sent whatever Orchestrator loaded (up to 20 messages) with no local-side bound at all.
2. **Possible interactive-mode stdin wait.** The previous subprocess call passed neither `-no-cnv` nor an explicit `stdin=`, so it inherited Ciphlet's own interactive terminal stdin. Recent llama.cpp builds can auto-enter a conversational mode for chat models that, after producing one reply, waits on stdin for the next turn instead of exiting — which would hang indefinitely on an inherited, never-EOF stdin until killed by the timeout. This is consistent with, though not independently confirmable as, part of the observed failure.

**Fix (`ciphlet/brain/local_provider.py` only):**
- New `_fit_history()`: estimates a conservative (character-based, intentionally low chars/token) token budget from `n_ctx`, always preserves the full system prompt untouched, and keeps as much of the *most recent* conversation as fits — oldest messages dropped first, current turn always kept. Applied before building the ChatML prompt.
- Added `-no-cnv` to the `llama-cli` invocation (forces single-shot completion instead of any auto conversation mode) and explicit `stdin=subprocess.DEVNULL` (guarantees no stdin read can ever block, regardless of build/flag behavior).
- `CIPHLET_LOCAL_TIMEOUT_S` was deliberately left unchanged (still 180s) — the fix is bounding the input and closing the interactive-mode risk, not widening the timeout, per instruction.

**Mac-side verification (proportional — no real Pi/model access):**
- Reconstructed the exact reported shape (12 prior messages + system prompt) and confirmed `_fit_history` trims it to fit within the 2048-token budget while always preserving the full system prompt and the current turn, and confirmed short conversations are left completely untrimmed (no unnecessary context loss).
- Confirmed via a stand-in script that `-no-cnv` is present in every invocation and that `stdin=subprocess.DEVNULL` actually prevents a simulated stdin-wait hang (returned in ~0.2s against a 10s timeout, where it would otherwise have hung the full 10s).
- Re-ran the full `--local-only` / `Orchestrator` / `BrainRouter` routing test (cloud leg stub raises if ever called) and all four failure-path tests (unconfigured, missing binary, missing model, non-zero exit) — all still pass unchanged.
